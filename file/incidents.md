# 치명적 오류 기록

서비스 핵심 기능이 아예 동작하지 않거나, 사용자에게 잘못된/깨진 결과가 보였던 오류들의 기록.
사소한 UI 다듬기는 여기 넣지 않고, 기능 자체가 망가졌던 것만 남긴다. 고칠 때마다 계속 추가할 것.

---

## 이미지 풀 관리자 페이지 업로드 전체 실패 — 원인 두 가지 (2026-09-08)

- **증상**: `/imageadd`에서 이미지를 올려도 항상 "0/N장 업로드 완료"만 뜨고 실제로는 하나도 등록 안 됨.
- **원인 1**: `api/admin-persona-image.ts`가 `persona-image-pool` Storage 버킷에 곧장 업로드를 시도했는데, 로컬 시드 스크립트들과 달리 버킷을 미리 만들어주는 코드가 빠져 있었음. 아무도 로컬 스크립트를 먼저 실행한 적이 없어서 버킷 자체가 존재하지 않았고, 그래서 모든 업로드가 "Bucket not found"로 실패.
- **원인 2**: 버킷을 만들어준 뒤에도 계속 실패 — Supabase Storage 객체 키(파일 경로)는 비-ASCII 문자를 허용하지 않는데, 태그(예: "몽글몽글함")를 폴더처럼 경로 앞에 그대로 붙이고 있어서 한글이 섞인 키가 전부 "Invalid key"로 거부됨.
- **수정**: (1) 업로드 전에 버킷을 idempotent하게 생성하는 코드 추가. (2) 파일 경로에서 태그를 완전히 빼고 랜덤 UUID 이름만 쓰도록 변경 — 태그는 어차피 DB의 `tags` 컬럼에 저장되니 경로에 인코딩할 필요가 없었음. 같은 패턴을 쓰던 로컬 스크립트 두 개도 동일하게 수정.
- **교훈**: (1) 같은 리소스(버킷)를 쓰는 진입점을 여러 개(로컬 스크립트, 서버 API) 만들 때는 "준비 단계"(버킷 생성 등)를 전부 복제했는지 확인할 것. (2) 클라이언트가 실패를 `res.ok`만 보고 조용히 넘기면 원인 파악이 몇 배로 오래 걸린다 — 실패 시 서버가 보낸 에러 상세를 항상 화면에 노출할 것.

## 관심사가 무시되고 엉뚱한 캐릭터 이미지가 나옴 — 이름이 사물/동물 명사였음 (2026-09-08)

- **증상**: 온보딩 대화에서 "떡볶이 좋아함"이라고 답했는데, 캐릭터 이름이 "토끼"로 지어지고 실제로 토끼 그림이 생성됨.
- **원인**: 온보딩 모델이 대화 내용을 반영하지 않고 흔한 귀여운 이름("토끼")을 임의로 지었고, 이미지 생성 프롬프트가 `이름: 토끼`를 그대로 Imagen에 넘겨서 그 단어의 사전적 의미(동물)가 그대로 그려짐.
- **수정**: (1) 온보딩 프롬프트에 "사물·동물을 그대로 가리키는 일반명사는 이름으로 쓰지 말 것", "언급된 관심사는 반드시 반영할 것" 규칙 추가. (2) 이미지 생성 프롬프트에 "이름은 애칭일 뿐 사전적 의미를 그대로 그리지 말 것" 명시. (3) 근본적으로는 캐릭터 이미지를 사용자별 실시간 생성에서 사전 제작 이미지 풀 매칭으로 바꿔서, 사용자가 지은 이름이 이미지 생성 프롬프트에 들어갈 일 자체를 없앰.
- **교훈**: 사용자가 자유롭게 짓게 한 텍스트(이름)를 다른 AI 파이프라인(이미지 생성)의 입력으로 그대로 재사용하면, 의도한 "이름"이 아니라 "지시문"으로 해석될 위험이 있다 — 특히 그 텍스트가 실제 사물·개념과 겹치는 단어일 때.

## 전체 AI 기능 마비 — ERR_MODULE_NOT_FOUND (2026-09-07)

- **증상**: 음성 기록, 텍스트 기록, 새 계정 온보딩 대화까지 전부 안 됨. `/api/structure-log`, `/api/onboarding-chat`, `/api/generate-diary` 세 개가 전부 `FUNCTION_INVOCATION_FAILED`(500)로 죽음.
- **원인**: `package.json`에 `"type": "module"`이 있어 Vercel Node.js 런타임이 상대 경로 import를 네이티브 ESM으로 해석하는데, 직전에 추가한 공용 유틸(`src/lib/textSanitize.ts`) import에 확장자가 빠져 있었음(`from '../src/lib/textSanitize'`). 같은 파일들의 기존 `import type { ... } from '../src/types'`는 컴파일 시 완전히 지워지는 타입 전용 import라 이 문제를 겪지 않았는데, `textSanitize.ts`가 `api/` → `src/` 경계를 넘는 첫 실제(값) import였던 게 문제를 처음 드러냄.
- **수정**: import 경로에 `.js` 확장자 명시(`'../src/lib/textSanitize.js'`). TypeScript가 `.js` 확장자를 형제 `.ts` 소스로 정상 해석해줌.
- **교훈**: `api/*.ts`가 `src/` 아래 값(함수·상수)을 새로 import할 때는 반드시 `.js` 확장자를 붙일 것. 로컬 `tsc --noEmit`으로는 이 문제가 안 잡히고, 실제 Vercel 배포에서만 터진다 — `vercel logs`로 런타임 로그를 봐야 알 수 있었음.

## 반복 글자로 깨지는 캐릭터 정보 (2026-09-04, 두 차례)

- **증상**: 온보딩/캐릭터 재구성 대화에서 캐릭터의 말투(tone) 필드가 "...자연스럽게 대화해요오오오오오오오오오오오..."처럼 같은 글자를 반복하며 깨짐.
- **원인**: `gemini-3.5-flash-lite` 모델이 드물게 반복 루프에 빠짐(라이트 모델의 알려진 불안정성). 1차 수정(글자 수 60자 제한)만으로는 반복이 제한 글자 수 안에서 시작되는 경우를 못 막아서 재발.
- **수정**: 길이 제한 전에 "같은 글자 3번 이상 연속"이 나오는 지점에서 먼저 잘라내는 `stripRepetition()`을 추가(`src/lib/textSanitize.ts`). 이후 소비/일정/사건 추출 필드, 다이어리 본문까지 동일한 방어 로직을 확장 적용.
- **교훈**: 프롬프트로 "반복하지 마라"고 지시하는 것만으로는 이 모델의 반복 루프를 완전히 막을 수 없다 — 서버 코드에서 결과를 사후 검증·정제하는 안전장치가 항상 필요.

## 체크박스가 눌러도 반응 없음 — PostgREST 1:1 임베드 (2026-09-04)

- **증상**: 일정·할일 완료 체크박스를 눌러도 체크 표시가 안 됨. 소비 카테고리 재지정도 같은 이유로 동작 안 함.
- **원인**: `task_status`/`consumption_override` 테이블의 기본키가 곧 `raw_log`를 가리키는 외래키라(1:1 관계), PostgREST가 이를 배열이 아니라 객체(또는 null) 하나로 내려줬는데, 코드는 배열로 가정하고 `task_status?.[0]?.completed`처럼 접근하고 있었음.
- **수정**: 타입과 접근 코드를 전부 `{ completed: boolean } | null` 형태(배열 아님)로 수정.
- **교훈**: PostgREST에서 자식 테이블의 기본키가 부모를 가리키는 외래키와 같으면(1:1), embed 결과가 배열이 아니라 객체로 내려온다 — 새로 embed를 추가할 때마다 이 점을 먼저 확인할 것.

## 생일이 "사건"으로 잘못 분류됨 (2026-09-04)

- **증상**: "OO는 내 생일이야" 같은 말이 일정이 아니라 사건(event)으로 저장되어, 매년 반복 표시가 전혀 뜨지 않음.
- **원인**: 기존 일정(schedule) 분류 기준이 "시각·장소가 있는 약속"이었는데, 생일은 시각·장소가 없어서 이 기준에 안 맞았고, 모델이 계속 사건으로 잘못 분류함(관찰됨: 이 모델은 이런 예외적 분류 기준을 안정적으로 못 따라감).
- **수정**: 분류 프롬프트에 예외 규칙 추가 + 모델이 뭘로 분류했든 키워드(생일/기념일 등)가 있으면 서버에서 무조건 schedule + recurring으로 강제.
- **교훈**: 이 모델에게 다지선다형 판단(카테고리, 타입 분류)을 통째로 맡기면 예외 케이스에서 계속 흔들린다 — 결정적인 판단은 서버 키워드 매칭으로 옮기고, 모델 출력은 참고만 하는 패턴을 기본으로 삼을 것.

## 소비 항목이 전부 "기타"로 분류됨 (2026-09-04)

- **증상**: 어떤 소비를 기록해도 카테고리가 항상 "기타"로만 나옴.
- **원인**: 타입 분류·필드 추출과 함께 카테고리 선택까지 한 번의 모델 호출에 맡겼는데, 지시가 많아지자 모델이 카테고리 지침을 안정적으로 못 따라가고 거의 항상 "기타"로 응답함.
- **수정**: 카테고리 결정을 모델에서 완전히 떼어내 서버 키워드 매칭(`inferCategory`)으로 전환.
- **교훈**: 위 "생일 오분류"와 같은 근본 원인 — 한 번의 호출에 판단거리가 많아질수록 이 모델의 정확도가 떨어진다.
